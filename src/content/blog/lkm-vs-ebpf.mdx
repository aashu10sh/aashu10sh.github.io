You want to run some code at the kernel mode ( ring 0 ), do you? 
> When I say "kernel mode" I mean code running with kernel privileges, in kernel context with access to kernel memory. 

The kernel space should be taken with great seriousness, access to it should be done very sparsely and avoided unless absolutely necessary and we should execute programs in the user-space as much as possible. One of the reasons is because the maximum damage a buggy user-space program could do from a execution perspective is a program tripping over itself and crashing ( i mean bugs and not someone intentionally destroying things like rm -rf /, a fork bomb and what not), A buggy user-space program does not cause a kernel panic or cripple the operating system. The kernel ensures this. When a program runs in user-space, the all-encompassing kernel with the help of the CPU's hardware protections ensures that the program is not doing anything naughty. Unfortunately we do not have this fail-safe for programs that run in the kernel space - if a program does something it should not, if a kernel space program runs into a bug and crashes, its over 🥀

Ok so clearly we need to be extra careful when running things in the kernel space, so why do we need to write programs that run at ring 0 ( kernel space )? Turns out user-space has its limitations and there are some things that can only be done at the kernel level, this is because the kernel sits between every program and the hardware, it sees everything: all memory, all devices, all packets and all scheduling decisions. A user-space program can only see what the kernel chooses to show it.

1. hardware - 
device registers, interrupts and DMA are all exclusive to the kernel. if you are making a driver for a hardware device ( nic, gpu, custom usb gadget) you have no option but to write that code in the kernel space.
> user-space drivers do exist, such as VFIO, UIO, and DPDK, but they still rely on a kernel piece to set them up
2. observability - 
the kernel sees every systemcall, every context-switch, every packet, every file in the device. This level of visual access gives kernel space observability programs incredible advantage, you can answer questions like "why did this request take 200ms?" or "does this program persist to disk after every write?" from the kernel which is efficient as opposed to using something like ptrace from the user-space.
3. performance - 
say you are building a program that needs to read a network packet and need to make a decision on wether to let it pass or drop it, if you are sending each packet to the user-space to decide this then your app is too slow, making this decision on the kernel when the packet arrives avoids that cost.
4. security - 
a user-space program could watch events and react but it cannot stop them reliably. An attacker with higher privilege can simply kill it and move on with their malicious plans. Since the kernel is the one point where everything has to pass through and you need "this process can never read that file" guarantees, the only option is to run these checks in the kernel and this is exactly what LSM hooks are for.

Ok, so how do you **safely** run code in the kernel space?

We have two primary ways? the newer eBPF and the traditional LKM.

## LKM
LKM stands for Linux Kernel Module and the Linux Kernel has had loadable modules since the mid 1990s. They have been the traditional way of running code in the kernel space for the longest time, it was the default way. Before kernel modules, every driver you needed had to be compiled into one big kernel image which was not very efficient for a development perspective. Kernel modules let the kernel stay lean and load code only when needed, for example when you plug in your hardware. LKM are mostly used to implement device drivers but they can also be used to implement network protocols, crypto libraries, rootkits and SIEM systems. 

The biggest problem by far with Linux Kernel modules is that they could potentially corrupt the kernel memory and cause unexpected behaviour. When a kernel module de-references a bad pointer it causes an kernel oops and the kernel logs a stack trace, kills the task that was running and keeps going but now the its "tainted" and may be unstable. The kernel might run into a full panic if the if the earlier fault happens to interrupt the context in a critical path or if `panic_on_oops` is set. The quieter failures like memory corruption, deadlocks and leaks stay around even after you unload the module.

Linux Kernel Modules also don't have a stable in-kernel API and an out-of-tree module can break with any kernel update and must be rebuilt for every version. This is why DKMS exists and why Nvidia, ZFS and Virtualbox run into problems after upgrading. Many Kernel symbols are also `EXPORT_SYMBOL_GPL` so only GPL-licensed modules can use them.

## eBPF
eBPF stands for Extended Berkeley Packet filter and it is an extension to the classic BPF which was a tiny virtual machine for filtering packets ( fun fact: tcp dump uses bpf ). eBPF was introduced to the linux kernel in kernel 3.18, it moved to 64 bit registers and added maps, helper functions and many other hook types beyond just packets. Today, eBPF is more than just the packet filtering tool it was originally created to be, it does a lot of things.

This is how you would run a eBPF program:

1. Write your kernel side program ( normally in restricted C, or in rust with the aya framework which is also quite nice). 
2. Compile the kernel space program with llvm(clang for c and rustc for rust) to eBPF bytecode, which produces an ELF object.
3. Your loader loads the program in kernel space with the `bpf()` syscall.
4. The verifier which is inside the kernel checks the bytecode, 
> The verifier does more than just check for unbounded loops and recursions, it walks every possible path and does memory access bound checks, stack size checks and ensures type-correct calls.
5. The JIT compiler inside the kernel compiles it to native machine code ( some kernels also have a interpreter for fallback )
6. Your loader attaches it to a hook, where it runs every time it fires.
7. You also write a user-space loader which communicates with its kernel space counterpart and exchanges information using maps or ring-buffers.

As you can see eBPF has better restrictions, better primitives and a really good ecosystem with tools like tetragon and cillium leading the way.

## The Successor
For most use-cases, it would not be far-fetched to call eBPF the successor to LKM. It works perfectly for 90% of LKM's use-cases while providing user's with a modern, safer system. eBPF's verifier makes it impossible for an eBPF program to taint the system and potentially corrupt the kernel and cause a full-blown panic. eBPF's "Co-RE" (Compile once, run everywhere) architecture is also a key reason why eBPF is better for modern systems because with eBPF users don't have to recompile for every kernel version. Linux modules are established a rootkit vector in the industry, well known LKM rootkits have existed in the industry for decades. An eBPF program on the other hand is limited but not harmless, if a bad actor uses eBPF primitives to do something malicious then eBPF modules can be misused.

## A case for LKM
LKM's are still widely used and very powerful because an eBPF program can extend the kernel where the kernel has provided a hook or an interface for it. A kernel module on the other hand can extend the kernel anywhere. The main use-case for an LKM is still device drivers, you cannot yet reliably use eBPF for device drivers. Long running background work, self-implemented kernel threads or very complex logic that exceeds the verifier limit are still good use-cases for a Linux Kernel. eBPF's architecture is best suited when you have to do some task in reaction to an event in a system, if you need to change kernel behaviour where no hooks, helper functions, or kfunc exists, eBPF cannot do it. I think using rust to implement kernel modules is a good really way to build kernel modules because of rust's memory model and advanced safety features eliminate potential trivial bugs like nil pointer defer, use after free, double free at compile time, giving you kernel module extra security.

## Conclusion
Ok, you clearly want to do this, I see you! ask yourself this question "does this need to be in the kernel space?" if it does not, great! write something in user land. If your answer to the previous question was yes then ask yourself another question "is there a hook for what I am trying to achieve? ( is my action in-reaction to an event? )?" if your answer is yes ( which it will be for 90% of the time) use eBPF and if not use Kernel Modules ( in rust if possible ).
